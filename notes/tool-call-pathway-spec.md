# Tool-Call Pathway Spec (M2c)

Reference for writing prompts and native markdown agents against OpenCode V2 tool
naming. Prompt text and frontmatter must use V2 tool names. V1 names
(`bash`, `task`, `write`, `patch`, `apply_patch`) are silently ignored under V2: a
denial on an unknown name is not enforced, and a prompt that tells an agent to call
`bash` addresses no tool.

## 1. V1 -> V2 tool-name map

From `V1_TO_V2_TOOL_NAME` in `agent-tool-restrictions.ts` and `V1_TO_V2_ACTION` in
`agent-config-converter.ts` (identical rename set).

| V1 name | V2 name | Notes |
|---|---|---|
| `bash` | `shell` | permission action too |
| `task` | `subagent` | permission action too |
| `write` | `edit` | `write`, `patch`, `apply_patch` all collapse to `edit` |
| `patch` | `edit` | collapse |
| `apply_patch` | `edit` | collapse |

## 2. Per-agent tool surface (V2)

Semantics (`session-tools-store.ts`): under V2 a tool mapped `false` is DENIED and
is removed from the callable surface; a tool mapped `true` is positively present
even when a default would omit it (`deriveRemovedToolNames` / `deriveAllowedToolNames`).

Records are normalized by `normalizeToolRecord` before launch, then merged in the
order `base -> userDenied -> getAgentToolRestrictions(agent)`, so an agent-specific
denial overrides a base `true`.

### 2a. Per-agent expected surface (`PER_AGENT_TOOL_SURFACE`)

Derived by `buildPerAgentToolSurface()` from `getAgentToolRestrictions`
(`normalizeToolRecord` + worker read-side baseline). `allowed` = keys mapped `true`
(positively present); `removed` = keys mapped `false` (denied). `team_*` is the 12
`TEAM_TOOL_DENYLIST` entries (section 2d); the list column shows only the
agent-specific additions. "13 read-side" = `WORKER_READ_SIDE_TOOLS` (section 2c).

| Agent | Class | `allowed` (positively present) | `removed` (beyond the 12 `team_*`) |
|---|---|---|---|
| `sisyphus` | orchestrator | - | - |
| `planner` | planner | - | `edit` |
| `sisyphus-junior` | worker | 13 read-side | `subagent` |
| `worker` | worker | 13 read-side | `subagent` |
| `executor` | worker | 13 read-side | `edit`, `call_omo_agent` |
| `advisor` | advisor | - | - |
| `explore` | read-only | - | `edit`, `subagent`, `call_omo_agent` |
| `librarian` | read-only | - | `edit`, `subagent`, `call_omo_agent` |
| `research` | read-only | - | `edit`, `subagent`, `call_omo_agent` |
| `reviewer` | manager | - | `edit` |
| `catalog-researcher` | researcher | - | - |

Notes:

- `worker` resolves to `sisyphus-junior` (`resolveAgentKey`), so both rows are
  identical. `sisyphus-junior`'s `AGENT_RESTRICTIONS` entry denies V1 `task`, which
  normalizes to `subagent`.
- `planner` and `reviewer` deny V1 `write` and `edit`; both collapse to the single
  V2 `edit` key.
- `executor` denies `write`/`edit`/`call_omo_agent`; the read-side baseline is still
  added on top.
- `explore` / `librarian` / `research` share `EXPLORATION_AGENT_DENYLIST`
  (`write`, `edit`, `task`, `call_omo_agent` -> normalized `edit`, `subagent`,
  `call_omo_agent`).
- `advisor` and `catalog-researcher` have no `AGENT_RESTRICTIONS` entry, so the map
  itself only removes `team_*`. Their factories deny more on the **registered**
  agent (advisor: `write`/`edit`/`apply_patch`/`task`/`call_omo_agent`;
  catalog-researcher: `write`/`edit`/`apply_patch`) - see `advisor.ts` /
  `catalog-researcher/index.ts`.

Delegated-child launch base (`buildSyncPromptTools` sync, `launchTools` background)
is layered on top of `getAgentToolRestrictions`: `subagent = canSpawnWorkers(agent)`,
`call_omo_agent = true`, `question = false`, then the restriction map is spread last
(so an agent-specific `subagent: false` wins). `team_*` is included unless the child
is a team run.

`canSpawnWorkers` returns true for plan-family (`plan`, `prometheus`) always, and
for manager/dispatcher agents (`MANAGER_AGENT_NAMES` = `planner`, `executor`,
`reviewer`; `DISPATCHER_AGENT_NAMES` = `manager`) only when `delegation.managers`
is enabled. Its result is NOT part of `PER_AGENT_TOOL_SURFACE`; the manifest's
`allowed`/`removed` reflect `getAgentToolRestrictions` only.

### 2b. sisyphus (primary, not a delegated child)

sisyphus is the orchestrator, so the launch base above does not apply. Its surface
comes from the factory (`sisyphus-agent-config.ts`): `subagent` allow, `edit` allow,
`call_omo_agent` deny, `question` allow. It has no `AGENT_RESTRICTIONS` entry
(`PER_AGENT_TOOL_SURFACE.sisyphus.removed` is the 12 `team_*` only). For frontier
models (Claude Opus 4.7+, GPT-5.5/5.6), `getFrontierToolSchemaPermission` also
denies `grep` and `glob`.

### 2c. Worker read-side baseline (`WORKER_READ_SIDE_TOOLS`)

Added as `true` for `EXECUTION_AGENT_NAMES` = {`sisyphus-junior`, `worker`,
`executor`} when not already set. 13 tools:

```
codegraph_status  codegraph_explore  codegraph_search  codegraph_context
codegraph_node    codegraph_callers  codegraph_callees codegraph_impact
codegraph_files   skill              skill_mcp         websearch   webfetch
```

Live-gate nuance: the manifest's hard `requiredPresence` gate for worker-class agents
is `WORKER_PRESENCE_GATE` = {`codegraph_explore`, `skill`, `websearch`, `webfetch`}
(the full read-side list stays in `allowed` as the documented intended surface). The
live sandbox can only assert `livePresenceGate` = {`websearch`, `webfetch`}: OpenCode's
MCP-to-model wiring does not expose codegraph in that environment, and `skill`
invocation is non-deterministic for the runbook model. codegraph/skill presence is
proven at code level by the unit tests against `PER_AGENT_TOOL_SURFACE`.

### 2d. Team tool denylist (applied to every non-team delegated child)

All mapped `false` under V2: `team_create`, `team_delete`, `team_shutdown_request`,
`team_approve_shutdown`, `team_reject_shutdown`, `team_send_message`,
`team_task_create`, `team_task_list`, `team_task_update`, `team_task_get`,
`team_status`, `team_list`.

## 3. Prompt snippets (V2 names only)

Paste-ready fragments. Command/delegation/edit references use V2 names (`shell`,
`subagent`, `edit`); never the V1 names `bash`, `task`, `write`.

Exception: the M2d continuation handle is written `task({ task_id, answer })`. That
is the literal form the question router emits, and the delegate/continuation tool is
registered as `tools.task` in the plugin; its V2 permission action is `subagent`
(section 1). Do not use `task` for anything else.

Use `shell` for commands, tests, and builds:

```
Run the focused suite with `shell`:
  shell({ command: "bun test packages/omo-opencode/src/tools/delegate-task" })

Use `shell` for git, package managers, and test runners. Do not describe shell
commands as "bash".
```

Delegate work with `subagent` (not `task`):

```
Spawn a worker with `subagent`:
  subagent({ subagent_type: "worker", prompt: "...", run_in_background: true })

Delegate read-only exploration with `subagent`:
  subagent({ subagent_type: "explore", prompt: "Where is X defined?" })
```

Spawn named read-only agents with `call_omo_agent` (only `explore` and `librarian`):

```
call_omo_agent({ agent: "explore", prompt: "Find the auth flow." })
call_omo_agent({ agent: "librarian", prompt: "How does <library> implement Y?" })
```

Apply changes with `edit`:

```
Apply each change with `edit` (one atomic edit per call).
Use `edit` for file writes and patches. There is no `write` or `patch` tool.
```

Read-side helpers for execution agents:

```
Use `codegraph_explore` / `codegraph_search` for structure, `skill` to load a skill,
and `websearch` / `webfetch` for external docs.
```

Subagent questions route to the orchestrator by default (M2d):

```
A delegated worker that needs a decision calls the `question` tool. By default the
question routes to the orchestrator, not the user. The notification carries the
continuation id; answer it with the `task` continuation form and the `answer`
parameter:

  task({ task_id: "<task_id from the question notification>", answer: "Use `shell`." })

`answer` is a `task` parameter (added in M2d). Supplying it resolves the pending
child question in place - no new delegation runs - and the worker continues from the
orchestrator's answer. A `task_id` with no pending question returns
"No pending question for task ...".

Escalate to the user directly only when the decision is genuinely the user's
(credentials, product direction, irreversible choice). The worker forces that with:

  question({ questions: [...], route: "user" })

`route: "user"` bypasses the orchestrator and presents the native dialog unchanged.
If the orchestrator does not answer within `questionOrchestratorWaitMs` (default
120000 ms), the question escalates to the user automatically.
```

Tool-discipline directive block (copy verbatim into any agent prompt):

```
## Tool discipline (V2 names)

- Commands and tests: `shell`.
- Delegation: `subagent` (delegated workers) and `call_omo_agent` (`explore`/`librarian`).
- File changes: `edit`.
- Structure: `codegraph_*`. Skills: `skill` / `skill_mcp`. Web: `websearch` / `webfetch`.

Never reference `bash`, `task`, `write`, `patch`, or `apply_patch`: those names do
not exist under V2 and are ignored.
```

## 4. Permission frontmatter examples (Phase 3 native markdown agents)

Phase 3 authors `.opencode/agents/<name>.md`. The V2 frontmatter shape (from
`agent-file-emitter.ts`) is: `description`, `mode`, `permissions` (a LIST of
`action` / `resource` / `effect` rules), optional `steps`, `color`, `disabled`,
`request.body`. The Markdown body is the system prompt.

Rules:

- `permissions:` is plural and is a list. Each entry has `action`, `resource`,
  `effect`. `effect` is `allow` | `deny` | `ask`.
- `action` uses V2 `shell` / `subagent` / `edit` (NOT `bash` / `task` / `write`).
- `resource` is `"*"` for a whole tool, or a pattern (for `shell`, a command pattern).
- Do NOT add a `model` field: omit it to preserve `/models` session-model inheritance.
- Do NOT add a `tools` field: V1 `tools` maps have no V2 frontmatter home.

Template:

```markdown
---
description: "<one-line role>"
mode: subagent
permissions:
  - action: edit
    resource: "*"
    effect: deny
  - action: subagent
    resource: "*"
    effect: deny
---
<system prompt body>
```

Worker / sisyphus-junior (executes, does not delegate; keeps the read-side set):

```markdown
---
description: "Focused task executor. Same discipline, no delegation."
mode: subagent
permissions:
  - action: subagent
    resource: "*"
    effect: deny
  - action: edit
    resource: "*"
    effect: allow
  - action: codegraph_explore
    resource: "*"
    effect: allow
  - action: skill
    resource: "*"
    effect: allow
  - action: websearch
    resource: "*"
    effect: allow
  - action: webfetch
    resource: "*"
    effect: allow
---
<worker system prompt>
```

Explore / librarian / research (read-only, no delegation):

```markdown
---
description: "Read-only codebase search specialist."
mode: subagent
permissions:
  - action: edit
    resource: "*"
    effect: deny
  - action: subagent
    resource: "*"
    effect: deny
  - action: call_omo_agent
    resource: "*"
    effect: deny
---
<exploration system prompt>
```

Planner / reviewer (manager, spawns workers, never edits):

```markdown
---
description: "Manager-layer planner. Produces a work plan; never edits."
mode: subagent
permissions:
  - action: edit
    resource: "*"
    effect: deny
---
<planner system prompt>
```

Executor (manager, spawns workers, never edits, no direct agent calls):

```markdown
---
description: "Manager-layer executor. Delegates to workers; never edits directly."
mode: subagent
permissions:
  - action: edit
    resource: "*"
    effect: deny
  - action: call_omo_agent
    resource: "*"
    effect: deny
---
<executor system prompt>
```

Shell command scoping (optional, uses the per-command `resource` pattern):

```markdown
---
description: "Agent allowed to run tests but not destructive git."
mode: subagent
permissions:
  - action: shell
    resource: "bun test *"
    effect: allow
  - action: shell
    resource: "*"
    effect: ask
---
<prompt body>
```

## 5. Common mistakes

V1 names that silently do nothing under V2:

| Written | Problem | Use instead |
|---|---|---|
| `bash` in prompt text or permission | no such tool/action; the denial is not enforced and the prompt addresses nothing | `shell` |
| `task` in prompt text or permission | no such tool/action | `subagent` |
| `write` in prompt text or permission | no such tool/action | `edit` |
| `patch` in prompt text or permission | no such tool/action | `edit` |
| `apply_patch` in prompt text or permission | no such tool/action | `edit` |
| `delegate_task` in permission | legacy; migrated to `task` then `subagent` | `subagent` |

Other traps:

- `tools:` in a native markdown agent frontmatter: no V2 field. Use `permissions:`.
- `model:` in Phase 3 frontmatter: pins the agent and breaks `/models` inheritance.
  Omit it.
- A denial for a non-existent name is ignored by the server, so the tool stays
  callable. Verify the action name exists (`shell` / `subagent` / `edit`).
- `write`, `patch`, and `apply_patch` all collapse to the single `edit` action, so
  denying `write` alone does not deny `patch` unless `edit` is the action you deny.
- Delegated children always get `question: false` in the launch record, so they
  cannot raise a native user dialog directly. Instead their `question` call routes
  to the orchestrator by default (`route: "user"` forces immediate user escalation);
  the orchestrator answers via `task(task_id=..., answer=...)` before the bounded
  `questionOrchestratorWaitMs` window elapses (M2d).
- `call_omo_agent` is only for `explore` and `librarian`. Delegating anything else
  uses `subagent`.
