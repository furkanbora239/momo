# OpenCode v2 native migration

The native runtime is an OpenCode v2-only surface. It uses the v2 provider, model, integration, session, permission, and TUI APIs directly; the V1 client/config adapters are not part of this path. Native role visibility remains owned by OpenCode.

The two-tool contract is `momo_task` for task work and `momo_consult` for consultations. `momo_task` exposes create, resume, select, answer, cancel, status, wait, list, candidates, detail, and result. `momo_consult` exposes start, select, status, wait, list, candidates, detail, and result; consultation requests are recorded with kind `consultation`. Callers do not supply a role or session identity: the runtime derives the caller from its server context and scopes status/wait operations to the root lineage. A route may return a selected model, an `awaiting_selection` response with candidates, or `unavailable`. Selection revalidates the current provider/model state, hard-allow pool, role rules, and caller ownership without invoking Jev again. Invalid input and authorization failures are surfaced as clear errors; router or Jev unavailability becomes a persisted manager-visible result instead of an implicit model fallback.

The model-facing lifecycle definitions are small discovery envelopes generated from the authoritative action names. They preserve the existing flat call format, but every handler still validates the complete request against its original strict per-action schema after checking the native caller role. Extra fields do not confer model, role or session authority. Request `help` for an unfamiliar operation rather than assuming the initial envelope is its complete signature. OpenCode owns Code Mode execution; momo adds no second MCP server or sandbox.

Both lifecycle tools expose `help` (optionally `operation`) and `capabilities`. Help returns a versioned operation index or an input schema generated from the same strict validator used for execution. Cache help by contract version; refresh capability information when provider or advisor settings change. Capabilities distinguish an empty advisor pool from no eligible advisor, and report the calling role's delegation and question support. Workers discover these through `momo_consult`, since they cannot use `momo_task`. Native `question` asks for missing information; consultation requests reasoning advice from an explicitly configured eligible advisor. Capability discovery never changes a binding or authorizes another role.

Task-returning actions accept `view: "brief"` to omit repeated policy/activity metadata and result text. Brief responses preserve identity, state, errors, question identifiers, result availability and relevant `nextActions`; use `detail` or `result` when more evidence is needed. The default/full response remains compatible. Interrupted task errors are exposed in either view. Lists and candidates retain explicit pagination.

Native model tools return JSON text through the OpenCode content protocol. In Code Mode parse once: `const task = JSON.parse(await tools.momo_task({ action: "create", prompt: "..." }));` then use `task.id` and `task.decisionId`. `list` recovers task IDs and summaries only within the caller's parent/root ownership scope; internal maintenance work is counted and appears with `includeMaintenance: true`. List and candidate pages accept `offset` and `limit` (maximum 10); candidate pages also accept role/provider filters. Use the exact offered role/model and decision ID for manual selection.

Status and wait expose compact execution state, role policy permissions and bounded activity without persisted event history or historical candidate menus. A successful execution leaves `execution.verification` unknown; it does not prove acceptance. Role permissions describe policy capabilities, while native resource authorization still applies. Worker is the direct shell/edit role; executor, planner and reviewer coordinate workers. Result previews are bounded by UTF-8 bytes and expose `resultTruncated`/`resultLength`. Use the `result` action and follow `nextOffset` to retrieve all text; offsets and lengths are JavaScript UTF-16 string indices. `detail` exposes bounded assignment fields and native question keys/titles/options. The backend task engine and readonly RPC retain full internal records for CLI/runtime use.

At the root, `orchestrator` may route directly to a worker or use `planner`, `executor`, or `reviewer` as a department lead. Department children are worker roles. Worker roles can request consultation but cannot delegate. `advisor` can only handle consultation and cannot delegate or consult. The advisor model pool is the project `.omo/omo.jsonc` setting `[opencode].manager.advisor_models`, with the existing momo config layering rules. It is intersected with the general model pool. An empty advisor pool disables consultation. The `/advisor-pool` TUI panel edits that setting; `/pool` controls the general hard-allow model pool and `/providers` controls provider availability. An empty general pool means all models are allowed; it does not disable task routing.

Tasks persist their root, parent, session, decision, attempt, progress and delivery identities. Native execution events determine completion without requiring `session.idle`; durable execution sequence numbers reject old finishes. Completion and parent delivery are separate. Retried results and forwarded question forms reuse stable IDs. A child question first reaches its parent, then escalates to the root user after the configured question timeout. Managed department wakeups reserve provider/model capacity through the scheduler, and a department waiting for children releases its generation slot.

Restart reconciliation inspects existing native sessions. Finished work is delivered without rerunning; native aborted executions resume in the same session with their original assignment. Explicit cancellation stops the department tree and remains cancelled after restart. When inspection confirms an execution has stopped, resumption discards its expired active-tool leases. A genuinely running native session keeps its current tools and is not prompted again. The production silence and active-tool timeout defaults remain 180000 and 3600000 ms.

The Jev router sees the full task brief and all currently eligible connected candidates, including unknown price and capability fields as unknown. It must not substitute an unverified free price or ability. Unknown facts remain unknown during selection. Only a dispatched, selected unknown model enters the durable per-project maintenance queue; catalog snapshots never launch researchers. Research stays visibly paused with `executor_unbound` unless `[opencode].catalog.research_executor` explicitly binds `{ "providerID": "...", "modelID": "..." }`. The bound executor must remain connected, tool-capable, pool-allowed, and eligible for catalog research. One maintenance job runs only while user task generations and their root session are idle. Completed jobs are not rerun after restart; an uncertain launch stays paused for inspection. Maintenance uses the native task engine, does not ask for caller selection or questions, and does not post root result notifications. Native provider failures that explicitly identify training on request data and privacy settings quarantine only the actually rejected model in its project for one hour. Replayed old failures do not extend expiry; routing remains without silent fallback or privacy-setting changes. The native `momo_catalog_enrich` tool accepts only source-backed HTTP(S) profiles and requires both the exact runtime agent ID `momo-catalog-researcher` and a baseline-owned agent check, excluding user agents that reuse the name. Research profiles stay separate from runtime outcomes. Low confidence, Jev failure, malformed answers, exhausted budget, or circuit-breaker state returns caller options; no other model is silently chosen. A versioned JSONL ledger retains the request, candidate snapshots, Jev response/probabilities or failure evidence, caller selection, actual runtime dispatch, and runtime outcome. Outcomes are based on task runtime state; verification stays `unknown` unless runtime evidence supports a stronger label.

The pinned Codebase Memory MCP candidate remains disabled by default. Fixture QA found that source changes were not visible until a full manual reindex (`automaticFreshness: false`), so its search results are not safe as a default source of truth. The pinned binary, cache, and runtime stay under managed task-specific roots; no installer or global MCP configuration is used. The integrated fallback registrar builds v2 MCP configs for bundled LSP and ast-grep. Real isolated QA exercised worker rewriting and advisor readonly search, including a denied rename. Native dialog/keymap TUI controls loaded through server plugin config and persisted isolated pool/provider/advisor settings.

Isolated built-plugin probes on OpenCode 2.0.24 passed pricing, five parallel workers, department routing, caller selection, consultation role boundaries, questions and escalation, busy-parent delivery retries, server restarts, cancellation, active shell timeout protection and native permission denial. They use local mock providers and Jev, and prove unchanged user database counts and process cleanup. This proves the exercised harness contracts, not a performance success rate on production models.
