### F11 — Multi-Harness Monorepo Deadweight vs OpenCode Focus
- Symptom: Monorepo contains 45 packages (`omo-codex`, `omo-senpi`, `senpi-task`, `pi-goal`, `pi-webfetch`, `omo-native`, 12 platform launcher binaries, `web` marketing site). `package.json` build coordinates 17 build nodes. Tests report irrelevant environment failures from other harnesses (e.g. 3 Codex component failures).
- Root cause: Upstream OMO's roadmap prioritized generic multi-harness abstraction over OpenCode simplicity.
- Clash with MOMO: MOMO is strictly OpenCode-targeted. Carrying the deadweight packages causes slow builds, confusing workspace dependencies (e.g. `packages/omo-opencode` declaring dependency on `omo-codex`), and mental friction when navigating the codebase.
- Planned action: Decouple or isolate non-OpenCode adapters; create an ultra-fast OpenCode-only build command (`bun run build:opencode`).

### F12 — Monolithic Prompt Bloat vs Fast/Cheap Model Reality
- Symptom: System prompts for orchestrator variants in `packages/omo-opencode/src/agents/sisyphus/*.ts` range from 10KB to 32KB per model (e.g. `gpt-5-5.ts` is 32KB, `claude-opus-5.ts` is 26KB).
- Root cause: Upstream OMO was engineered under the assumption of a giant flagship LLM (Claude Opus / GPT-5) with 200k context and 32k thinking token budget.
- Clash with MOMO: MOMO uses whatever model is chosen in OpenCode `/models` (Gemini Flash, Kimi, GLM, etc.) and delegates to cheap fast models. Injecting 30KB prompts exhausts token budgets immediately and causes thinking-model token exhaustion (such as GLM 5.2 hitting output caps).
- Planned action: Replace the per-model prompt behemoths with a unified, lightweight MOMO orchestrator prompt template (~2KB-4KB) focused on hard delegation, concise tool calls, and minimal tokens.

### F13 — Chat-Turn Context Injection Hooks vs Token-Efficiency North Star
- Symptom: Dozens of hooks execute on each message turn (`agentUsageReminder`, `categorySkillReminder`, `rulesInjector`, `repoMapInjector`, `teamModeStatusInjector`, `btwSideContextInjector`, `todoContinuationEnforcer`).
- Root cause: Upstream OMO relies on continuous in-band prompting and reminder injection to babysit long autonomous runs.
- Clash with MOMO: Every single hook injects lines of markdown into the message history on EVERY turn. This silently burns thousands of tokens per session. MOMO's core mandate is maximum performance per token.
- Planned action: Default-off all reminder and status injector hooks; gate rule injection verbosity; keep context payload minimal.

### F14 — Tool Schema & Description Overhead (Wave 6)
- Symptom: Built-in tools and MCP definitions have extensive multi-paragraph descriptions and large parameter schemas that are sent in the system prompt on every API call.
- Root cause: Upstream OMO tools were written with verbose documentation for models needing high explanation.
- Clash with MOMO: Wastes input tokens on every turn. Modern frameworks (e.g. Claude Code) use compact tool descriptions (≤600 characters).
- Planned action: Implement Wave 6: trim tool descriptions to ≤600 characters per `notes/claude-code-patterns.md`.

### F15 — Config Schema & Migration Churn (`oh-my-openagent.json` vs `omo.json`)
- Symptom: Dual schemas, legacy workspace migrations, and startup console warnings during session initialization.
- Root cause: Upstream OMO is in the middle of a rebranding/unification transition between config formats.
- Clash with MOMO: Clutters logs with non-actionable migration warnings.
- Planned action: Standardize on a single clean `~/.omo/omo.jsonc` format without noisy migration logs.
